# 开发指南

本项目使用 ESM，无第三方构建依赖，需要 Node.js 20 或更新版本。安装和使用方法见 [README](../README.md)。

## 构建与检查

在仓库根目录执行：

```sh
npm run build
npm run check
```

`build` 生成 `themes/*.json`、`lib/client.js`、`lib/client.assets-*.js` 和本地配色预览 `docs/preview.html`。`check` 运行测试、检查生成文件是否与源码一致，并验证 Harness checkout 的兼容性。提交时应包含更新后的生成文件；本地预览不提交。

图片数据按主题写入带内容哈希的客户端分块，主文件保留目录与配色。激活插件前通过 Harness 的 `require.async` 加载分块，再注册完整皮肤；沿用同一包内的图片数据，画质与离线使用方式不变。分块适用于 Web 与 Desktop 的模块载入通道，避免单个生成文件超过 GitHub 的 100 MB 限制；单个分块控制在约 1 MB 以内，避免 Windows Defender 把含大量 base64 图片的单行脚本误报为 `Trojan:Script/ObfusScript.A!ml` 并隔离，导致 `loadAssets()` 因缺少分块而拒绝、整个主题插件加载失败。`compatibility.json` 同时记录模块加载器及其分块能力；升级 Harness 时复查 `ClientBundleRequire.async` 和 `ClientBundleRegistration.chunk`。

## 连接 Harness 源码

将本仓库与 Harness 仓库放在同一级目录，分别命名为 `dsh-theme` 和 `deepseek-harness`，然后执行：

```sh
npm run dsh:link
npm run dsh:check
```

命令按 `--harness <path>`、环境变量 `DSH_HARNESS_ROOT`、`../deepseek-harness` 的顺序查找 Harness。例如：

```sh
npm run dsh:link -- --harness /absolute/path/to/deepseek-harness
```

`dsh:link` 构建主题、链接到 `web` profile 并检查配置。`dsh:check` 检查兼容性和主题配置；链接依赖损坏时，使用 `npm run dsh:repair` 修复。需要启动服务时，使用 `npm run dsh:start`，可追加 `-- --no-open` 禁止自动打开浏览器。

开发期间保留正在运行的 Harness 服务，优先复用它检查效果。需要独立测试服务时，为该进程设置独立的 `DSH_HOME`，在 Harness 源码仓库执行 `pnpm dsh --profile web --port 0 --no-open`。记录测试进程，并在验证完成后仅关闭该进程。

## 源码与素材

| 路径 | 用途 |
| --- | --- |
| `families/*.mjs` | 主题名称、配色与装饰参数 |
| `families/categories.json` | 主题分类 |
| `families/assets/` | 提交到仓库的 WebP 素材 |
| `lib/client.tpl.js` | 客户端行为与设置界面源码 |
| `scripts/gen-themes.mjs` | 主题与客户端生成器 |
| `lib/index.js`、`cordis.patch.yml` | 插件入口与集成配置 |
| `docs/screenshots/` | 公开展示截图 |

修改客户端行为时，编辑 `lib/client.tpl.js` 后运行构建。`lib/client.js`、`lib/client.assets-*.js` 和 `themes/*.json` 为生成文件。

原始图片、素材处理脚本和检查截图放在仓库外的本地目录，通过 `DSH_THEME_DEV` 指定。该目录包含 `raw/` 和 `outputs/`，素材处理脚本从仓库根目录运行。素材目录和 Harness 运行目录均应位于非同步磁盘目录中，分别存放。日常运行保持 `DSH_HOME` 未设置，使用 Harness 默认的 `~/.dsh`。

## 主题显示名

有明确子主题的系列采用「主题 · 子主题 · 名字」，中英文层级一致，分隔符统一为两侧有空格的 ` · `。

| 层级 | 含义 | 示例 |
| --- | --- | --- |
| 主题 | 作品、IP 或角色系列 | 咕嘎和 Doro / Guga & Doro |
| 子主题 | 可容纳多套设计的题材、世界观或角色分支 | 江湖 / Jianghu、日常 / Daily Life、植物大战僵尸 / Plants vs. Zombies、魔法师 / Wizard Life |
| 名字 | 本套设计的场景或故事 | 竹涧茶歇 / Bamboo Creek Tea、睡莲护航队 / Lily Pad Patrol |

完整名称如「咕嘎和 Doro · 江湖 · 竹涧茶歇」。咕嘎和 Doro 是系列名；单角色或双人场景在简介中说明。已有「EVA · 初号机 · 觉醒」等明确分支沿用同一层级含义。没有稳定子主题的系列保留「主题 · 名字」；只有作品名的旧主题也可保留，新增设计先确定具体故事名。

简约是外观变体，在完整名称后加 ` · 简约` / ` · Minimal`；简约家族从父家族的 `names` 派生名称，避免两处维护。浅色、深色和跟随系统属于外观模式，通过模式选项展示。

主题库按中文显示名的拼音顺序排列，名称中的数字按数值比较，`sortKey` 不再参与排序；默认主题固定在最前，简约项继续紧随父主题。收藏页保留最近收藏在前的顺序，轮换名单保留用户选择的顺序。修改显示名时保持 Family ID、皮肤 ID、素材文件名和 `kin` 不变。同步维护中英文名称、README 目录、完整图库及 Obsidian 制作记录，并重新生成客户端目录与皮肤 JSON。

## IP 原作画风与参考范围

未明确要求更换画风时，动漫和游戏主题以各自原作官方视觉为准，保留人物比例、脸型、眼睛、发型、服装、线条、上色与渲染语言。不能把用户对Doro某一系列的手办、毛绒或微缩偏好套到其他IP。游戏原作使用二维、三维或插画时分别遵循原作，不统一转成二维。

参考图须同时记录身份和画风用途。只有用户明确指定时才跨IP转换材质与比例。视觉验收先核对原作辨识和神态，再检查素材完整性、透明边缘、布局及对比度；技术通过不等于风格通过。原作比例在侧栏过小时可使用半身构图，不能擅自Q版化。

## 先确认右下角场景

同一组浅色与深色主图分别设计，须在动作、镜头、构图、人物组合、服装或具体场景等方面形成清晰可辨的差异，不能复用完全相同的画面，也不能仅调整亮度、配色、光照或日夜背景。两种模式可以延续同一故事与角色关系，不要求更换人物。总览必须同时展示每组的浅色与深色方案，验收时逐组并排检查差异。

新主题、重新设计和多图拓展统一采用以下顺序，用户明确要求跳过确认时除外：

1. **先出一张场景总览。** 直接生成分镜式总览，集中展示拟用的右下角图片，而不是先完成所有正式素材再拼图。标明场景和浅深色；四组独立浅深色方案可用两行八格。让人物身份、服装、动作、视角、轮廓与必要布景清楚可辨，手脚和道具接触有足够细节，不先制作整套界面。第一版生成后先交用户审阅场景方向；发现脚部、手部、裁切或道具接触等局部问题时，随图简短注明待修项，不在用户看图前自行反复修图。
2. **围绕总览修改。** 等用户选定保留的场景并提出意见后，再按需集中处理场景调整与局部问题，避免为可能被舍弃的场景提前打磨。根据用户意见编辑最新总览中有分歧的场景，保留已经认可的格子，每轮展示更新后的完整总览。此时不扩展横幅、物件、文件夹、侧栏角色和主题配置，避免场景未定就产生整套返工。
3. **明确确认后展开。** 用户认可总览后，以确认版和各格裁切参考逐张制作正式主图，再设计配套装饰、配色并接入主题。延续已确认的角色组合、服装、动作与镜头；不直接把总览小图当成最终素材，也不在制作中另起构图。明显改动需先更新总览并重新确认；没有回复不视为同意。
4. **检查正式素材与界面。** 逐张核对头颈、肩胯、膝踝、鞋尖朝向、承重、遮挡和道具接触，再处理透明边缘并验证浅深色、系统模式及窄屏。场景确认不代替细节验收。

总览版本、提示词、场景与模式编号、确认记录放入仓库外的素材目录，例如 `raw/<family>/scene-sheet-v01.png`；保留明确的确认版本供后续制作引用。

## 右下角主图的克制动效

沿用透明主图的构图、镜头和主体姿态，把动效放在画面已有的少量细节上。让亮度变化有起落和间歇，让有接触点的元素在原位摆动并保持接触关系，让位于透明空白区的独立飞行器或悬浮道具按缓慢非对称周期轻轻悬停。正常阅读时动效留在余光里，不抢夺正文注意力。

### 技术方案：静态原图 + RGB 控制遮罩 + 原生 WebGL

为避免整图预渲染动画 WebP 造成的包体膨胀（单套主题动辄 10+ MB）与降采样清晰度损失，本项目统一采用 **静态原图 + 256×256 RGB 控制遮罩 + 零依赖原生 WebGL 着色器** 方案：

- **零额外主图体积**：运行时直接复用现有的满分辨率静态主图（`--dsw-pack-wallpaper`），每个动态场景仅额外提交一张 256×256 的 RGB WebP 遮罩 `<family>[-<variant>]-motion-mask-<mode>.webp`（通常仅 1–2 KB，四景八图总增量仅 ~10 KB）。
- **单 WebGL 上下文 + 省电与回退**：
  - 在 `#dsh-themes-veil` 内挂载单一 `<canvas id="dsh-themes-motion-canvas">`，帧率上限锁定 **30 fps**，输出严格合法的预乘 Alpha（`rgb <= alpha`），确保浅深纸底均无杂边。
  - 宽屏清晰模式下，通过轻量 2D 镜像画布（`.dsh-themes-motion-composer`）将底部帧同步绘制到输入框保护渐隐之上、输入框控件之下，不创建第二个 WebGL 上下文。
  - 页面切到后台（`document.hidden`）、系统启用「减少动态效果」（`prefers-reduced-motion: reduce`）、视口收窄至 `≤900px`、或宿主不支持 WebGL 时自动停帧并无缝回退到静态主图；关闭右下角角色时隐藏主图。
  - 在主题的「精细控制 → 主图动效」提供「静态 / 动态」切换，默认动态，按主题持久化并随场景及浅深模式切换。

### 遮罩通道与参数规范

256×256 RGB 遮罩图三个通道各司其职（0 = 静止，255 = 最大权重）：

| 通道 / 字段 | 负责对象 | 常用模式与要点 |
| :--- | :--- | :--- |
| **`R` 通道（`fluid`）** | 火焰、烟尘、云雾、水面波纹、火花 | `sway`（烟尘/云雾/布料，接触点权重 0、尖端 1）、`flame`（向上滚动噪声 + 暖色微闪）、`water`（纯水平波纹轻荡，船身/岸边留安全边距）、`spark`（高频微幅光斑颤动）。着色器只在遮罩邻域内采样，不拉扯周边刚体。 |
| **`G` 通道（`glowA`）** | 警示灯、光束、战术屏幕、喷口、飞行器镜头 | `beacon`（每 4 秒同步短亮至高光再回落至暗色，沿用 ZZ 小样节奏）、`breathe`（柔和呼吸）、`beam`（光束能量波纹流动）、`screen`（终端扫描线与柔和呼吸）。 |
| **`B` 通道（`glowB`）** | 机体眼部、建筑/船舱窗灯、辅助灯带 | 独立缓慢正弦呼吸（`breathe`），与主发光错开周期避免机械同步。 |
| **`floaters`（最多 4 组）** | 位于透明空白区的独立飞行器、浮游炮、悬浮物 | 在配置中提供归一化包围盒 `rect: [u0, v0, u1, v1]` 与支点 `pivot: [cx, cy]`，着色器直接将原位挖空并用双非整数倍正弦波做平滑上下浮动、水平漂移与微倾角（`ampX`、`ampY`、`ampRot`、`speed`、`phase`、`glowSpeed`），无需复制底图或单独切小图。若悬浮物与主体有遮挡重叠，则需先在仓库外素材目录拆层并用 LaMa/IOPaint 补底。 |

在 `families/<family>.mjs` 中按场景 ID 与浅深模式声明 `wallpaperMotion`（生成器 `scripts/gen-themes.mjs` 会自动校验对应 `<prefix>-motion-mask-<mode>.webp` 并将其并入该主题的图片分块）：

```js
wallpaperMotion: {
  original: {
    light: {
      floaters: [
        { rect: [0.11189, 0.19556, 0.24913, 0.33333], pivot: [0.18861, 0.27259], ampX: 0.0032, ampY: 0.0115, ampRot: 0.032, speed: 1.18, glowSpeed: 1.85 },
      ],
      fluid: { mode: "sway", ampX: 0.0042, ampY: 0.0024, freq: 16, speed: 0.85 },
      glowA: { mode: "beacon", color: [1, 0.78, 0.3], haloColor: [1, 0.58, 0.14], period: 4, intensity: 0.75, dim: 0.68 },
      glowB: { mode: "breathe", color: [1, 0.92, 0.42], period: 5.5, intensity: 0.48 },
    },
    dark: { /* ... */ },
  },
}
```

### 制作与验收步骤

1. **分析场景要素**：在静态透明主图上用连通域与色域分析，区分「独立透明区刚体（`floaters`）」「软体/流体（`R`）」「主发光（`G`）」「次发光（`B`）」。每个场景只挑 2–4 处已有细节，保持主体构图绝对稳定。
2. **生成遮罩并目视核验**：先生成全分辨率通道权重再缩放为 256×256 RGB WebP 写入 `families/assets/<prefix>-motion-mask-<mode>.webp`。**必须同步输出调试叠层图**，逐张核对：
   - 流体遮罩（`R`）与手指、脚尖、装甲边缘、船体或地面接触点之间无溢出；
   - 悬浮包围盒（`floaters.rect`）四周有充足透明留边且与主体零重叠；
   - 发光遮罩（`G`/`B`）不误伤相邻同色涂装或地标虚线。
3. **接入配置与测试**：在 `families/<family>.mjs` 补齐 `wallpaperMotion` 参数后运行 `npm run build`、`npm run check`，并在 Harness 实测浅色/深色、柔和/清晰、空会话 Hero 页与长对话页、输入框遮挡层、窄屏回退及「静态 / 动态」切换。

## 添加主题

在 `families/` 中创建小写连字符命名的 `.mjs` 文件，参考现有主题导出 `id`、`names`、`light`、`dark` 和装饰参数。每个氛围主题都应提供简约配对；简约主题复用基础配色，通过 `kin` 指向氛围主题，并在设置列表中相邻显示。同步更新分类后运行构建。

素材按以下规则命名：

| 素材 | 文件名 |
| --- | --- |
| 角色壁纸 | `<family>-light.webp`、`<family>-dark.webp` |
| 侧栏角色 | `<family>-pal-N.webp`，序号从 1 开始 |
| 场景横幅 | `<family>-banner-light.webp`、`<family>-banner-dark.webp` |
| 文件夹图标 | `<family>-folder[-open]-<mode>.webp` |
| 左下角物件 | `<family>-props.webp` 或 `<family>-props-<mode>.webp` |
| 主图动效遮罩 | `<family>[-<variant>]-motion-mask-<mode>.webp`（256×256 RGB，可选） |

氛围主题必须提供浅深色横幅。横幅使用无角色的场景插画，比例约为 6:1，主要景物位于右侧三分之一、靠近垂直中部，其余景物延伸至画面中部。左侧 0–25% 与右侧 90–100% 渐变至对应氛围主题的 `paper` 色，并设置 `decor.headerArt.bakedHorizontalFade: true`。使用 `scripts/build-banners.py` 裁切原始素材，分别调整浅深色图片的裁切位置。新增主题使用横幅；`<family>-panel.webp` 仅用于现有主题的兼容。

使用本地 `docs/preview.html` 检查配色，并在 Harness 中检查浅色、深色、跟随系统及窄窗口效果。公开截图应使用无个人会话、路径或账户信息的演示环境。

大屏清晰模式的左下道具在输入框保护背景之上、实际控件之下绘制。输入框可能通过 `will-change: transform` 建立固定定位包含块，因此其装饰使用局部绝对定位，并根据实测位置换算窗口坐标；不能通过关闭上游合成层或写死侧栏宽度修正。调整时同时检查侧栏展开／收起、输入框增高、底栏高度变化和滚动；退出清晰模式、缩小窗口或卸载插件时应清理尺寸观察与位置变量。

README 首页采用精选展示：保留用户指定的条目，其他作品与系列各选一套，优先群像。同系列新增主题更新[完整图库](screenshots/README.md)与 README 的折叠目录；新作品可补充一套精选代表。完整图库始终包含全部主题和浅深截图。

主题设置页在 `≤600px` 时把宿主导航改为横向滚动，按钮高度 44px，并为内容区保留完整宽度。规则只在设置弹窗包含 `.dsh-theme-page` 时生效；调整主题控件时检查 390px 和 320px 视口及导航滚动。

## 从单图主题拓展为多图

本节仅适用于把已有单图主题拓展为多图的请求。从零设计新主题时，按主题自身的创意、需求和构图设计，不强制套用此扩展流程。两者都先按「先确认右下角场景」完成总览审阅，再制作正式素材。

保留原配图作比较，新增各组先确定独立故事和视觉重心。制作前列出人物组合与人数、镜头视角、整体轮廓、空间关系、动作节奏和叙事重心，检查场景之间是否在多项维度上存在清晰差异。人数可以相同，也可以减少或变化；不能默认要求所有角色每张都出现。仅换道具、表情、姿势细节或日夜光照，不足以说明拓展完成。

参考图明确标注人物身份、服装和画风用途；没有用户要求时，不继承原图站位、镜头与群像比例。可使用单人裁切参考，让各场景分别编写构图提示词，避免共用固定人数与前后站位的模板。继续遵守原作画风和统一阅读配色，但允许横向追跑、单人留白、俯视围坐等不同画面组织方式；这些仅为示例，不是固定场景清单。

交付前把原配图与所有扩展图并排比较，确认人物关系、画面轮廓和故事重心可以清楚区分，再核对每张浅深图的人体连接、关节、重心、遮挡和道具接触，最后检查透明边缘、装饰布局与窄屏。技术检查通过不能替代场景差异与人体结构验收。

## 收藏、主题轮换与同主题图片

客户端偏好保存在 `dsh-themes:pref`，文档版本为 7。根级 `appearance` 保存跨主题的精细控制：`header`、`character`、`props`、`pal` 四个装饰开关，以及 `headerRange`（`title` 限于标题栏 / `extend` 向下延展，默认 `extend`）。旧版采用当前选中主题的精细控制迁移；当前为原生外观时采用 `families.default`，无旧值则使用默认。切换主题与自动轮换沿用全局值，局部保存不覆盖未提供的字段；`mode`、`wallpaper` 和 `artwork` 继续按主题保存。根级 `favorites` 按收藏顺序保存稳定的主题 ID，去重并过滤失效条目；`library.tab` 保存主题库标签（`all` / `favorites`），`library.showMinimal` 保存简约可见性，更新时合并字段。

精细控制的恢复默认仅重置 `appearance` 五个字段，不改变明暗模式、清晰度、场景或轮播配置。横幅关闭或当前主题无横幅资源时禁用范围选择，但保留全局偏好。限于标题栏时保留原图绘制尺寸，由标题容器连同上下留白裁切，避免将图片和底部渐隐压缩成细条；向下延展时绘制在外层标题行。范围切换不改变标题行高度、宿主按钮裁切或交互。

“全部主题 / 我的收藏”是主题库中的常驻同级标签，独立于轮换开关。收藏页按最近收藏在前排列，支持搜索、分类、预览与应用；每页分别保留本次访问中的搜索和分类。收藏精确到单个条目，简约配对不会因分组搜索自动加入收藏结果；原生默认外观不参与收藏。卡片主体与星标使用并列按钮，避免按钮嵌套和收藏时误触预览。

根级 `rotation` 保存主题池、开关、播法、间隔和顺序，与收藏互不约束。播法二选一（v7 起携带 `mode`，旧配置按「到点就换」迁移）：`cycle` 播完再换按各主题插图间隔播完整轮勾选场景再切换；`fixed` 到点就换把间隔作为窗口上限，按插图间隔播完一轮即提前切换，装不下窗口时才均分压缩，播不完的场景由进度记忆留到下次接着播。轮换选择器的全部／收藏／已选标签共享临时勾选，搜索或切换范围不丢弃隐藏选择；完成后一次保存，取消、Esc、收起面板或离开外观页丢弃草稿。已有成员保留顺序，新成员追加。选择器独立维护浏览状态，不改变外部主题库标签；取消收藏不移出轮换，加入轮换不自动收藏，零收藏也可正常配置轮换。

每个 `families[id].artwork` 独立保存 `variant`、`known` 和图片轮换配置。没有保存开关时，多图主题默认开启、单图主题保持关闭；图片池默认勾选原配图与全部变体，间隔默认为 5 分钟，顺序默认为按列表。`known` 记录已经出现过的场景 ID：新增场景默认加入名单，已知场景的手动取消、自定义开关、有效间隔和顺序继续保留。旧版仅含 `original` 的默认名单，以及 `known` 只有原图的单图配置，扩展后一次升级为勾选全部现有配图、开启、5 分钟和按列表，保留当前场景与其他外观；升级结果立即保存。没有 `known` 的其他旧多图名单按已有选择保留并补记当前场景清单。旧文档只保存选中主题、没有主题独立设置时，计时器也使用该主题的图片默认值。根级主题轮换仍默认关闭。

单个节目钟统一推进两层轮换：节目单由当前主题的插图配置与主题轮换名单实时展开，每次触发要么换场景、要么跨主题，不会互相推迟。跨主题后按新主题的节目重新计时，并从上次停播的下一张场景接着播。

自动轮换只在本包主题已应用时运行。主题外观页、未结束的预览、页面隐藏、最近 15 秒的输入和宿主 `[data-streaming="true"]` 回复期间暂停。暂停结束后当前场景重新计满一拍，本轮已播进度保留，不补切后台错过的次数。随机模式排除当前项；主题名单不足两款时不跨主题，节目单退化为纯插图轮换。插件卸载时释放计时器和监听。

每个氛围主题自动包含保留 ID `original` 的原配图。后续在该主题的 `.mjs` 中声明额外变体，无需新增主题或皮肤 ID：

```js
artworks: [
  {
    id: "rain",
    names: { zh: "雨中小憩", en: "Rest in the Rain" },
    decor: {
      wallpaperSize: "min(34vw, 420px, 40vh)",
      wallpaperPosition: "right bottom",
      headerArt: { bakedHorizontalFade: true },
    },
  },
],
```

素材放入 `families/assets/`，前缀固定为 `<family>-<variant>`，例如 `gundam-rain-light.webp`、`gundam-rain-dark.webp`。变体 ID 使用小写英文与数字，以连字符分隔，同一主题内唯一，不得使用 `original`。

| 变体素材 | 文件名 |
| --- | --- |
| 主壁纸 | `<family>-<variant>-light.webp`、`<family>-<variant>-dark.webp` |
| 横幅 | `<family>-<variant>-banner-<mode>.webp`，或共用 `-banner.webp` |
| 文件夹 | `<family>-<variant>-folder[-open]-<mode>.webp` |
| 左下角物件 | `<family>-<variant>-props[-<mode>].webp` |
| 设置角色 | `<family>-<variant>-pal-N.webp` |

未提供的图片沿用原配图，可仅扩展主壁纸；没有任何有效素材、ID 重复或名称不完整时构建失败。主壁纸尺寸自动写入比例变量。浅深色分别检查；新横幅继续遵循无角色、对应主题纸色及两侧渐隐约定，不使用旧式 panel。

`decor` 可覆盖四个构图字段 `wallpaperSize`、`wallpaperPosition`、`heroTranslate`、`heroMaxWidth`，以及双语 `phrases`；其余部分继承原主题。变体通过图片分块加载，运行时只允许覆盖图片和构图变量，不能覆盖配色。原配图、清晰度和四个装饰开关均可继续使用。

## Harness 兼容性

### 侧栏角色的设置入口

Web 与 Desktop 的侧栏角色都直达“主题与外观”。主题等待 `settings.launcher` 声明后，将 `sidebar.settings` 当前有效注册的共享 Store handle 同时声明到角色所在的 `sidebar.footer.action`。渲染器管理实例并提供 `actions.openSection("themes")`；角色不自行创建 Store，也不模拟快捷键。Web 隐藏原有设置按钮，Desktop 保留账号菜单。设置声明撤销时，角色注册随之释放。

快捷键和原生菜单继续调用 Harness 的 `open` action；关闭设置时，设置壳会清除 `activeId`，因此下次通过这些入口打开时仍显示默认页面。角色按钮通过 `aria-label` 标明“主题与外观”，不设置 `title`，以免悬停提示遮挡角色短句。升级 Harness 时需复查共享 Store、`openSection`／`close` action 及侧栏两个插槽的 root scope。`tests/pal-settings.test.mjs` 覆盖两端角色选择主题页、可访问名称、原有按钮可见性和声明释放。Windows Desktop `0.2.1-alpha.2` 的实际验证与完整兼容基线分别记录在 README 中。

### 桌面端的系统外观

Electron 的 `nativeTheme.themeSource` 同时控制原生窗口外观和渲染器的 `prefers-color-scheme` 查询。Harness 根据 `html[data-ds-theme-source]` 同步该值；注册皮肤默认写入其解析后的浅深色。因此，主题在保存或预览模式为 `system` 时保持该属性为 `system`，再通过媒体查询选择对应皮肤；固定模式则同步当前皮肤的浅深色。

适配仅作用于本包的当前主题和默认外观预览。模式改变但皮肤 ID 未变化时也需同步；属性观察用于保持 Harness 重绘后的系统模式，卸载时释放观察并交还已解析的外观。升级 Harness 时需复查该原生同步属性。`tests/preferences.test.mjs` 覆盖手动外观切回系统模式、系统外观变化、固定模式、预览取消及观察释放。

### 版本验证

[`compatibility.json`](../compatibility.json) 记录已完整验证的 Harness 版本、客户端包和导出入口。`npm run check:compat` 会以基线提示版本差异；缺少包、导出或必要依赖仍是硬失败，版本号不同不等于不兼容，以实际 API 检查和真实界面验证为准。

`package.json` 中四个 `@deepseek-ai/dsh-client-*` 的 peer 范围供 Harness 判断运行时版本是否匹配。当前范围为 `^0.2.2-rc.1`，具体匹配遵循 semver 规则；版本匹配不代表已经完成兼容性验证。

更新兼容基线时，检查客户端 API 适配，运行支持版本的 CI，完成 Harness 构建、安装包安装和真实 Web 启动验证，再同步更新兼容记录、peer 范围及 README 兼容表。peer 范围应保持在已验证的版本线上，不跨越未经验证的主版本或次版本。

CI 每周一检查 Harness `master`。检查失败时，应分析上游变化并完成适配验证后再更新基线。

## GitHub Release

1. 更新 `package.json` 的版本号；有兼容性变化时，完成上述验证并更新兼容记录。
2. 运行 `npm run check` 和 `npm run release:pack`。
3. 检查 `dist/` 中的 `.tgz`、`SHA256SUMS.txt` 和发布说明。`dist/` 不提交到 Git。
4. 提交源码和生成文件，推送与包版本一致的 `v<版本>` 标签。
5. Release workflow 验证安装包并创建 GitHub Release 草稿。在草稿中补充本版主题、修复和兼容性变化，审阅后发布。

Release 使用 CI 验证过的同一份安装包。打包脚本检查文件清单和标签版本；安装包包含运行所需文件，图片已嵌入客户端。项目通过 GitHub Release 分发，`private: true` 禁止发布到 npm，但允许使用 `npm pack` 生成安装包。
